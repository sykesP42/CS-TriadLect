# dreamlab-rt P0 实现计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 交付一个零第三方依赖的 C++ 迷你引擎 + 关卡 0–3 的闯关式教学游戏，新生 3 条命令即可编译运行并动手改动。

**Architecture:** 三层单向依赖 `core`（平台/数学/光栅化/字模）→ `engine`（世界/材质/光照/控制台/热重载/存档）→ `game`（关卡内容与玩家）。渲染为软件光栅化；平台层同时提供 Win32 真窗口与无窗口离屏两种后端，后者用于自动化验证与 CI。

**Tech Stack:** C++17、Win32 API、std::thread、Python 3 + Pillow + fontTools（仅维护者用，生成字模）、CMake（备路径）/ 直接调用 cl.exe（主路径）。

**验证原则（本项目没有单测，替代方案是"看图 + 断言"）：** 每个里程碑都以「真编译 + `--shot` 导出 PNG + 用 Python 检查像素/人工看图」收尾；纯逻辑部分（数学、字模解析、PNG 编码）额外加 `--selftest` 断言。

**环境事实（已探明）：**
- 本机：VS 2022 Community（含 VC++ 工具链，`vswhere` 可用）、32 核、Python 3 + Pillow 12 + fontTools 4.60（无 brotli，走 woff1/zlib 路线）
- 联网：npmmirror / jsdelivr / PyPI / Gitee 通；github.com 不通（推送需代理或 Gitee 镜像）
- 中文字模来源：`@fontsource/fusion-pixel-12px-proportional-sc@5.3.0`（OFL-1.1），woff 内含 31,345 字形 / 17,573 汉字，unitsPerEm=1200（12px 设计）

**主构建命令（从 Git Bash 调用 MSVC）：**
```bash
cmd //c 'call "C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Auxiliary\Build\vcvars64.bat" >nul && cl /nologo /std:c++17 /O2 /EHsc /W3 /Fo:build\ /Fe:build\dreamlab.exe core\*.cpp engine\*.cpp game\*.cpp game\levels\*.cpp'
```

- [x] **Step 5:** 提交

> **实现偏差（已记录）**：改动检测从「比 mtime」改成「逐字节比对文件内容」。原因：mtime 在多数文件系统上只有 1 秒分辨率，而学生改参数的手速正是"改一下 → 切回游戏看一眼 → 再改一下"，两次存盘落在同一秒就会被漏掉，症状是"热重载时好时坏"。逐字节比对 2KB 文本是零成本，还白拿一个好处：存盘但内容没变不会误触发。监视逻辑在 `engine/reload.h`。
> **验证结果**：content 数据与代码默认值一致时，开/关 content 两条路径渲染出的 PNG **逐像素完全相同**（0/129600 像素有差异）；改 plastic 的 albedo 红→蓝后差异 0.904%（1172 像素，全部落在那个球上）；改文件 → `--watch` 在 2.0s 检测到并重新应用，其画面与「改完文件重启」逐像素完全相同；故意拼错字段名 → 报 `content/materials.txt:70: 未知字段 "roudhness"（是不是想写 roughness？）`，那一次改动被整个忽略，画面与改动前逐像素相同。

> **实现补充（已记录）**：
> ① **命令住 main.cpp，不住 console.h** —— 面板是"终端"，它不该知道世界是什么；命令通过 `Handler` 回调走出去。这条边界是后面 `R` 键、关卡脚本、热键都复用同一套命令的保证。
> ② **`--cmd` 与真人敲回车同路径**（都走 `Console::run`），所以离屏截图里能看到的，宣讲现场一定按得出来。
> ③ **面板折行放在 draw 里**（不是 print 里）：窗口一改大小，折行自己跟着重排，历史不用动。
> ④ **光标不闪烁**：闪烁会让同一帧的两次离屏截图不一致，而逐像素比对是本项目的验证主手段。
> ⑤ **`shot` 命令先按"此刻的世界"重绘一帧再存**：否则 `--cmd shot` 会拍到一帧都还没渲染的空缓冲；存的是干净世界（不含面板），面板挡住的底部也拍得全。
> ⑥ **`Console::panelHeight()`**：贴底的 HUD 状态栏必须让开面板，否则半透明面板会把它盖成一层灰影（真的叠过，截图里抓到的）。
> ⑦ **`reload` 的措辞分三种**：没变化 / 全部生效 / **有文件报错（"读了 N 个文件；报错的那几个整份没生效"）** —— 写坏一个文件时不能说"重新应用了 N 个文件"，学生会以为改动进去了。
> **验证结果**：`--cmd "ambient 0.5"` → 画面平均亮度 0.3517 → 0.3623（世界区域像素均值 130.84 → 134.69），上半屏逐像素差异 73.9% 且全部是"变亮"方向；只开面板（不加命令）与 M3.1 基线 640×360 **逐像素完全相同**（0/230400），即控制台不污染渲染；故意把 `materials.txt` 第 70 行拼错后敲 `reload` → 面板红字 `content/materials.txt:70: 未知字段 "roudhness"（是不是想写 roughness？）`，面板以上 62400 像素**逐像素未变**（一个字段都没生效）；`help/inspect/light/ambient/reload/shot/cls` 与三条错误路径（用法错、没有第 5 盏灯、没有这个材质）都在面板里正确回中文；自检 129 项全通过（含折行不丢字、面板高度与 `panelHeight()` 对账、缺字模不白屏）。
> **给 M3.4 的接口约定**：窗口后端的 `R` 键不要另写一条重载路径，直接 `con.run("reload")` —— 这样"按住 R"和"敲 reload"共享同一份措辞与红字报错。

> **实现补充（已记录）**：
> ① **输入先被"翻译"再进游戏**：键盘、鼠标、`--walk` 脚本喂的都是同一个 `InputState`，所以"离屏跑 300 帧模拟一直按 W"和玩家在窗口里按着 W 走的是同一条代码、同一堵墙。碰撞这种"多一厘米就穿模"的事，只有在离屏下能自动化验证时才敢说它对。
> ② **P0 不做重力、不做跳跃**（设计文档定的）：地是平的，"走路"只剩水平两轴，学生读得完也改得动（想加重力？`tryMove` 的 y 轴加一行，方向是敞开的）。
> ③ **碰撞用"轴分离 + 二分退回"**：先单独试 x 轴，撞了就二分找到贴边位置；z 轴再做一遍。好处是贴着墙斜着走不会被卡死 —— 另一个轴始终是自由的，手感是"沿着墙滑过去"。
> ④ **实体自带 `prompt`（准星提示）和 `command`（按 E 执行的控制台命令）**：交互、打字、`--cmd` 共用同一个解释器。关卡作者写一句 command 就能让东西动起来，不用碰 C++ —— 这是 M4 铺关卡的地基。
> ⑤ **按 E 会顺手把控制台翻开**，并写明"（看着「X」按下 E）"：命令的来龙去脉就在眼前，而不是"按了之后画面悄悄变了"。
> ⑥ **控制台开着时键盘全归它**（不然敲 `ambient` 里的 a/w/d 会顺手把人挪走 —— 第一次用就会骂人）；没开控制台时敲任何可打印字符直接开打并保住第一个字符（不用先知道 `~` 在哪）。
> ⑦ **限帧 60 + `timeBeginPeriod(1)`**：不锁帧这个循环会跑到 77 帧、吃掉 4.9 个核；锁住后 2.8 个核。系统定时器粒度默认 15.6ms 一档 —— `sleep_for(5ms)` 会睡成 15.6ms，60 帧直接掉成 30 帧，所以开窗时把粒度调到 1ms 并与 `close()` 配对还回去（Win10 2004 起只影响本进程）。`--fpscap 0` 不锁（量性能），`--fpscap 30` 省电。
> ⑧ **HUD 上的 FPS 是"玩家眼里的一秒多少帧"**（帧间隔的倒数，含限帧等待），不是渲染耗时 —— 限帧后这两个数能差三倍。渲染本身多快看 `--trace` 的 `work=`、帧间隔看 `period=`；离屏没有"帧率"可言，那边显示的仍是渲染吞吐。
> ⑨ **贴完屏幕才睡**（`present()` 在计时之内）：先算这一帧干了多少活，再决定睡多久；干不完就不睡，让帧率自己掉下去。

| 尺寸 | 4 线程 | 8 线程 | 32 核 | 给谁 |
|---|---|---|---|---|
| 960x540 | 36 帧 | 56 帧 | 57 帧 | 4 核及以下 |
| 1280x720 | 19 帧 | 37 帧 | 46 帧 | 8 核 |
| 1600x900 | ~15 帧 | 24 帧 | 41 帧 | 16 核及以上 |

> **（上表是修正过的，说清怎么错的。）** 这一档最初是拿**离屏 `--shot`** 的数字定的，而离屏不含推屏（present）那一步 —— 真实开窗比它好看两倍多。当时的表写的是"1600x900 → 19.8ms（51 帧）"，按它给开发机开了 1600x900，实测只有 **20 帧**，被当场看出来。根因是 `Framebuffer::toRGB8`：每帧新分配 4.3MB + 单线程跑 430 万次 `std::pow`。把它并行化 + 缓冲复用之后（`36290fb`），1600x900 回到 **41~45 帧**，分档阈值这才站得住。教训值钱的地方不在"算错了"，而在**量哪个数字取决于要优化的是哪一段**：离屏工具链是这个项目的验证主力，但它的数字不能拿来定开窗的性能参数（README 约定⑩第 ③ 条）。

> `--threads N` 会喂进同一个判断，所以 `--threads 4` 在开发机上也能拿到低配那一档（便于验收）。平台侧只剩 `fitWindowToScreen()`（原名 `defaultWindowSize`，现在只管"别开出一扇屏幕装不下的窗"：装不下按 16:9 缩、下限 640x360）。三个档位都真开窗量过客户区：4 线程 **960x540**、8 线程 **1280x720**、auto（32 核）**1600x900**。

> **③ 第 0 关故意没有解答条目 —— 这一条是"四关可自动达成"这句话的含金量问题。** 它的正解是改 `game/shaders/lighting.cpp` 的 `kAmbientStrength`，**编译期常数**，运行时改不了。实测另一条路走得通：在评委视线里点一盏灯（`pos -1.5 2.6 4.8`、`intensity 30`）就能读到 100%。但那是学生不会走的路径，把它算进来，"四关都能自动达成"这句验收结论就注水了。所以 `--auto` 对第 0 关**显式报告跳过**并说明原因，宁可少一关。当前结果：**过关 3 关、跳过 1 关**（计划 Step 3 写的是"四关"，按此修正）。
> **④ 判"通过"的标准得说清楚。** `--all-levels` 不喂解答时，四关**本来就该读 0%** —— 那是出厂状态，不是失败。所以冒烟的通过标准是"四关都判出合法分数、不崩"；喂了 `--auto` 时才升级成"**有解答的必须真的过关**，没过就是解答写错或判定漂了，当场红"。两个标准混在一起会得到"冒烟永远失败"的假红。
> **⑤ 自己踩的一个坑：`--all-levels` 只在离屏分支实现，而不给 `--shot` 时 `windowed` 判定为真。** 于是参数被整个忽略、窗口开着一直跑，看起来跟"命令没反应"一模一样（被 timeout 杀掉、什么也不打印）。修法是把 `--all-levels` 也算进离屏模式。**教训**：新加的参数要先问一句"它在哪条路径上被读到？另一条路径会不会把它吃掉"。
> **⑥ 出图时关号插在扩展名之前**（`build/x.png` → `build/x_level2.png`），四关各一张。注意不喂解答时这四张是**同一张**（世界状态没变，只有判定在变）；喂了 `--auto` 才是四张不同的（每一关的解答在它自己判分前应用上去）。

> **实施偏差（M5）**
> **① CMake 那两条命令要带 `--config Release` —— 计划里写的那条会构建 Debug。** VS 生成器是**多配置**的，`cmake --build build-cmake` 不带 `--config` 时 CMake 硬编码回退到 `Debug`；而一个软光栅化实时渲染器跑未优化版本，帧率差好几倍，照着 README 敲命令的人不会知道要加这个参数。CMakeLists 里把配置列表砍成只剩 Release（`CMAKE_CONFIGURATION_TYPES`，且**必须写在 `project()` 之前** —— 生成器在 project() 那步就把列表定下来了）。也试过 `CMAKE_DEFAULT_BUILD_TYPE`，VS 生成器明确拒绝该变量（只认 Ninja Multi-Config）。砍完之后不带 `--config` 会**明确报错**（"此项目不包含配置和平台组合 Debug|x64"）而不是悄悄给你一个慢二进制 —— 这符合本项目"宁可吵也不悄悄错"的一贯取舍。

> **⑤ 低配帧率用开窗口径，不是离屏。** 离屏不含推屏那一步，会好看两倍多 —— 这个坑在 T4.4 踩过一次（见那里的偏差⑥）。另外实测发现**帧率很吃机器负载**：同一台机器上开着别的重负载程序会掉到大约一半，所以 README 里把这一点明写了出来，并给出了可复现的测量命令。
